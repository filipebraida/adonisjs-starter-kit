# i18n

Locales are declared in `config/i18n.ts` (`supportedLocales`, `defaultLocale`); its loaders are found at boot, one per module with a `resources/lang/` folder. Translation JSON lives per module at `app/<mod>/resources/lang/<locale>/<namespace>.json`. The file name is the namespace, on the backend loader and on the frontend glob alike (`core.json` → `core.layout.navMain.dashboard`), so the file doesn't repeat `core.` inside. A module's main file is named after it; a module may hold others (`auth/…/errors.json` → `errors.*`, `users/…/validator.json` for VineJS messages). Backend uses `ctx.i18n.t('key')`; frontend uses `useTranslation()`. Locale detection runs as an HTTP middleware that prefers an `X-User-Language` header → a `user-locale` cookie → the browser's `Accept-Language`. Authenticated users have `User.locale` as the authoritative source: the switch endpoint writes both cookie and DB; every login flow syncs the cookie from `user.locale` if set.

## Rules

- **Adding a key requires an entry in every supported locale**. There is no auto-generate. Missing keys fall back to the default locale at runtime — the mixed-language UI is the symptom. Two checks guard it: the frontend `t` is typed from the `en` JSON files (`.adonisjs/client/i18n.d.ts`, generated by `pnpm ace codegen`), so an unknown key fails `pnpm typecheck`; and `app/core/tests/unit/resources/translations.spec.ts` fails when a locale lacks a key `en` has (or has one `en` lacks).
- **Key naming**: `<file>.<section>.<key>`. The prefix is the file name, the same on the server and the frontend; inside `<mod>.json` you don't repeat it. E.g. inside `core.json`:
  ```json
  { "layout": { "navMain": { "dashboard": "Dashboard" } } }
  ```
  and consumed as `t('core.layout.navMain.dashboard')`.
- **Frontend**: `useTranslation()` returns `{ t, changeLanguage, language }`. `t(key, params?)` supports ICU interpolation. The browser downloads only the current locale (and the fallback); `changeLanguage` loads a new one before switching. SSR bundles every locale.
- **Backend**: `ctx.i18n.t('key', params?)`. The i18n instance is bound to `HttpContext` by the locale-detection middleware. Use in controllers, actions (if `i18n` was in the input), and mail classes.
- **ICU interpolation**: `{name}` in the string, `t('key', { name: 'Alice' })` at the call site. Also supports plurals and selectors.
- **Validation messages**: VineJS uses the request's i18n instance through the messages provider bound in the locale-detection middleware. Localize by adding keys under `<field>.<rule>` in `<mod>/resources/lang/<locale>/validator.json`.
- **User preference**: `User.locale` is a nullable column. When authenticated, the switch endpoint updates both the cookie and `user.locale`. Login flows sync `user-locale` cookie from `user.locale` if set. Pre-login (marketing/auth pages) uses cookie / `Accept-Language`, never DB.
- **Enum labels are keys, not code.** Each enum value has a `<mod>.<enum>.<value>` key in every locale (`users.roles.admin.name`, `users.activity.events.roles_synced`); transformers ship the raw value and the screen translates it. The enum file never holds display text.
- **Server-built text is translated before it leaves the request**: mails get their strings in the action (see [[mail]]); a flash message uses `ctx.i18n.t(...)`.
- **`packages/ui` holds no keys.** A primitive takes its texts as props with English defaults (`labels` on `DataTable`, `emptyMessage`/`clearLabel` on the filters); a wrapper in `#core/ui` fills them from `t` (`#core/ui/components/data_table`).
- **Locale switcher UI**: `<LanguageSwitcher />` lives in every logged-in shell — see [[layout-shells]].
- **Adding a locale** means updating `supportedLocales` in `config/i18n.ts`, adding a folder under every module's `resources/lang/`, and confirming every key exists in the new locale.

## Workflow

### Add a translation key

1. Pick the module. If the string is shared UI (nav, buttons, layout), put it in `core`.
2. Open the JSON file for every supported locale: `app/<mod>/resources/lang/<locale>/<mod>.json`.
3. Add the same key path in every file with the localized value.
4. Frontend: `t('<mod>.<path>')` via `useTranslation()`.
5. Backend: `ctx.i18n.t('<mod>.<path>')`.
6. Verify parity: grep the key across `app/<mod>/resources/lang/*/` — it must appear in both locales. Present in only one → it falls back silently and ships a mixed-language UI.

### Add a new module's translations

1. Create `app/<mod>/resources/lang/<locale>/<mod>.json` for every supported locale (`make:module --i18n` does it).
2. Nothing to wire: `config/i18n.ts` and the frontend glob find the folder, and `pnpm ace codegen` types the new keys.

### Interpolation

```json
{ "welcome": "Welcome, {name}!" }
```

```ts
t('core.welcome', { name: user.fullName })
```

Plural / selector:

```json
{ "items": "{count, plural, =0 {No items} one {# item} other {# items}}" }
```

### Localize a validator message

Add to `app/<mod>/resources/lang/<locale>/validator.json`:

```json
{ "required": "This field is required" }
```

VineJS looks these up automatically because the messages provider is bound in the locale-detection middleware.

### Set a user's default locale programmatically

Use during invite / sign-up when the target's language is known:

```ts
await User.create({ email, locale: 'pt' })
```

The next login flow writes the cookie for them.

## Anti-patterns

- ❌ Adding a key in one locale but not the others — runtime falls back silently to the default and users see mixed languages.
- ❌ Hardcoding strings in components (`<span>Save</span>` instead of `t('core.save')`).
- ❌ A translation key inside `packages/ui` — the primitive takes the text as a prop; the `#core/ui` wrapper translates.
- ❌ Typing `t` as `(key: string) => string` — it switches the key check off; use `TFunction` from `#core/ui/hooks/use_translation`.
- ❌ Reading `req.cookies['user-locale']` directly instead of `ctx.i18n.locale` — bypasses the detection priority (header → cookie → Accept-Language).
- ❌ Persisting locale to the cookie without also updating `user.locale` when the user is authenticated — the switch endpoint handles both; don't reimplement.
- ❌ Deep key paths (`core.a.b.c.d.e.f`) — collapse the JSON tree, keep depth ≤ 3.
- ❌ Repeating the module prefix inside the JSON file (`core.json` with a `core` root) — the file name is the prefix.
